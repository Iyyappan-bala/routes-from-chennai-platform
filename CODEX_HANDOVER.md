## 1. Project overview and product vision

A premium, database-driven travel discovery and editorial platform. Public visitors browse
destinations (organized region → country → city) and read travel stories; editors/admins manage
content through an authenticated dashboard. This is a **separate product** from a university
assignment website (`routes-from-chennai.pages.dev`, a different repo) — the two must never be
merged, and this platform reuses only the *factual content* about three real places (Marina Beach,
Meenakshi Amman Temple, Brihadeeswarar Temple), not any code.

## 5. Known bugs and technical limitations (found during real testing, not assumed)

1. **MapLibre's web worker fails to load** — confirmed in both local Next dev (Turbopack) AND the
   actual Vinext/Vite Cloudflare production build. The marker renders; the tile layer does not
   (console: `Error: Worker failed to load. Check that the worker URL is correct.`). This is **P0**
   — see `CODEX_TASKS.md`. Likely needs explicit worker bundling configuration for
   maplibre-gl under Vite/Cloudflare Workers (research `maplibregl.setWorkerUrl` /
   `?worker` import conventions for this maplibre-gl version).
2. **Admin authorization is enforced by RLS + a client-side redirect, not a server-side session
   check.** RLS is the real security backstop (verified: a non-editor's write attempts are
   genuinely rejected by the database), but `/admin` itself only redirects client-side after
   checking the session in the browser — a stronger defense-in-depth layer (server-rendered guard)
   is still open work.
3. **Current deployment is on a temporary, unclaimed Cloudflare account** (`bow-astronaut`) that
   will eventually be reclaimed/expire — it was never meant as the permanent production target. A
   real, owned Cloudflare Workers project needs to be set up (see `CODEX_TASKS.md` P0).
4. `npm audit` reports some moderate/high vulnerabilities from fresh dependency installs — not yet
   reviewed or triaged.

## 6. Database architecture

13 tables: `profiles`, `regions`, `countries`, `cities`, `media_assets`, `categories`,
`destinations`, `destination_categories`, `stories`, `story_categories`, `destination_stories`,
`saved_destinations`, `saved_stories`. Full DDL in `supabase/migrations/0001_init.sql`. RLS pattern:
public `SELECT` where `status = 'published'` (or unconditional for reference tables), all writes
restricted to `profiles.role IN ('editor','admin')`. A trigger (`handle_new_user`) auto-creates a
`profiles` row with `role = 'visitor'` on every new `auth.users` signup.
**`0002_grants.sql` is not optional** — without it, PostgREST returns "permission denied" even for
the service-role key, because table-level Postgres GRANTs are separate from RLS policies. This was
a real bug found during cloud testing; both migrations are already applied to the live project.

## 7. Authentication and authorization

Supabase Auth, email/password only (no OAuth providers configured). `lib/supabase-browser.ts`
creates a session-persisting client used only in `/admin/*` client components.
`app/admin/page.tsx` checks `supabase.auth.getSession()`, then queries the user's own
`profiles.role`, and shows the dashboard only if `role` is `editor` or `admin` — redirects to
`/admin/login` otherwise. **This check is a UX convenience, not the real security boundary** — RLS
is. Do not "fix" this by weakening RLS; do strengthen it by adding a server-side check (see
`CODEX_TASKS.md` P0).
